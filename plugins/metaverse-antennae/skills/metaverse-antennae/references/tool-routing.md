# Tool routing

Use this order for multi-step Metaverse Antennae tasks.

## Scene construction through Authoring

Whole scenes, schools, courtyards, villages and reference-image reconstruction prioritize `AuthoringThreeSceneService.run` inside the same Authoring workflow as all other scene writes. Search from the user's intent, Doc the exact returned method, then call its documented runtime binding through `authoring_code_execute`. The existing binding is `globalThis.AuthoringSceneEditor.threeSceneService.run(source, {sceneName, replacePrevious})`. Do not first invoke or describe Catalog `run_three_scene_script`; those calls remain intercepted and return Authoring guidance without executing their captured handlers. The gate does not automatically translate source into Authoring code.

ThreeScene supports suitable trees, rocks, furniture, lamps and decorative geometry as well as buildings. Real assets are optional and may be interleaved by style, fidelity, materials, editability and cost. Ordinary isolated primitives, requested models, characters and monsters use their appropriate Authoring creation APIs; suitable procedural props can use ThreeScene. Respect explicit model/preset requirements. Water, lights, characters and gameplay need their actual capabilities.

Plan larger scenes as self-contained scripts by region or component. Each run may create at most 499 non-root Mesh/Group nodes, including descendants; there is no corresponding scene-total limit. Keep a shared coordinate plan and use sequential Authoring Execute calls with `replacePrevious:false` to preserve completed work. Grouping does not reduce node count, and scripts do not share local variables. Continue until all requested regions and details are complete; do not reduce the user's scope to fit one call. Only intentional replacement of all previous generated batches registered by this VM uses true.

Check the returned run summary's `ok/exact/state`, then use the documented `AuthoringThreeSceneService.readLastResult` through Execute when IDs or status are needed. Preserve the same `runId` across paged snapshot reads and retain the required identities before starting another run. Outer Execute accepts 64 KiB of source and waits at most 30 seconds; a timeout does not cancel generation. Reconcile the snapshot status before further mutation; never switch to Catalog or retry a potentially running creation. Domain Skills and Catalog remain supplemental references after a concrete Authoring discovery gap, not an alternate discovery route.

## Authoring-preferred mutations

Every task-facing tool enters one session-scoped Authoring gate before its original handler. Direct resource discovery exceptions are `asset_search`, `catalog_search(kinds=["resourceKind"])` without `game_object_id` or `applicable_only`, and `catalog_describe(kind="resourceKind", item_id=...)`; `capture` (viewport screenshots), `system_status`, `add_user_chat_memory`, and `add_team_experience` are infrastructure exceptions. `inspect` with exactly `projection="editor_mode"`, `"runtime_mode"`, or `"runtime_logs"` is a direct diagnostic exception. These diagnostics and `capture` require no Authoring discovery or fallback and preserve any pending route. Apart from proactive Memory retrieval below, Skill/non-resource Catalog discovery, other Inspect projections, other direct tools, executable Catalog, and Batch cannot run first. Their initial call only captures the tool and arguments, and the handler may run once through `authoring_route_fallback` after a proved Authoring gap. On `AUTHORING_ROUTE_REQUIRED`, treat `routing.queries` only as optional, non-exhaustive starting hints; the list may be empty. Search from the original intent with one precise query per independently owned intent. Once an exact callable symbol is found, Doc it once and stop synonymous Search. Compact Doc `pendingTypes` is not a recursive checklist. If the composed public APIs cover the request, execute the smallest bounded body through `authoring_code_execute` and perform exact semantic readback.

Within one current user task, keep a compact evidence set keyed by exact symbol. Exact Search/Doc results may cover later public Authoring mutations only when the editor session, active project and level, requested semantics, and documented symbols remain unchanged, and no declaration-changing operation, timeout, transport uncertainty, or other execution uncertainty occurred. Do not Doc the same symbol twice while that evidence remains valid. Reuse never crosses tasks, turns, restarts, `EDITOR_LEVEL_CHANGED`, active-project changes, or new symbols or semantics. It saves discovery calls only: every mutation still uses its own bounded `authoring_code_execute` and exact semantic readback. An unrelated captured fallback never inherits discovery evidence; the exact Catalog continuation below is the only cross-route exception.

Use `authoring_route_fallback` only when intent-level discovery returned no results or exact dependency-aware Search/Doc evidence proves a concrete missing operation or semantic. The supplied hints are not mandatory and cannot establish or limit the capability boundary. One top-level Doc is not proof that the dependency closure lacks coverage. The route ID is session-scoped and the captured handler is one-shot. Never fall back after `executed=true`, a timeout, transport uncertainty, or an unresolved partial write; reconcile state instead.

## Bounded Catalog continuation

After a successful fallback Catalog Search, directly Describe an exact returned `kind`/`id`; a successful Describe can be refined for that same item. Then call only its returned `invoke.toolset`/`invoke.tool` unchanged. Invoke still returns a new captured route and needs one `authoring_route_fallback` with the current operation's concrete gap reason, but the preceding Search/Doc evidence is retained: do not repeat discovery merely to satisfy the new gate. This does not authorize the write automatically.

This is an uninterrupted next-call chain in one MCP session, not a task-wide exemption. An unrelated call (including diagnostics or Authoring calls), failure, expiry, or concurrent intervening request ends it; Batch and arbitrary tools remain gated. Keep the same user intent and unchanged editor context; never use a previous task's chain. New capabilities still require discovery, and every mutation requires exact semantic readback. If the APIs already cover the task, continue with Authoring execution instead.

## Existing-object edits

When Authoring Search/Doc proves it cannot resolve the required existing-object identity, consume the captured Inspect call through `authoring_route_fallback`. Use `scene_overview` only for unknown identity, keep exact-name discovery bounded, and use returned real IDs. After a successful read-only fallback, continue the original task using still-valid Search/Doc under the reuse conditions above. Do not repeat discovery merely because fallback supplied the missing ID; discover only newly needed symbols or constraints. Each subsequent mutation still requires its own bounded authoring_code_execute and exact semantic readback. This does not authorize another captured fallback.

## UI work

Discover canvases and widgets with `inspect(projection="ui_tree")` or `inspect(projection="ui_detail", ...)`. Call `catalog_describe(kind="tool", item_id="build_screen", projection="input_only")` for a screen input and specialize `operation/ui.property.bind` by the known source `kind`; read `antennae://ui/schema` only if the requested custom tree needs definitions or multiple node branches absent from that exact description. Read only the needed sections from `antennae://skills/ui/{section}` or `antennae://skills/worldUI/{section}`. Then use `ui.build_screen`, `ui.bind_property`, or the world-mount Catalog operation. Use only returned canvas/widget GUIDs.

## Multi-domain gameplay

Identify the domains that own each requested fact, read only the corresponding needed `antennae://skills/{skill}/index` and `/body` sections, then use `catalog_search` and `catalog_describe` to resolve each exact Tool, Operation, or property. Do not load all declared dependency bodies automatically; load one only when its subflow is requested. For a pending invocation use `projection="input_only"`, plus ordered `selectors` for already-known discriminators such as `projection`, `action`, `kind`, `scope`, or `type`; use `ability_name` for Ability schemas. For a known property path describe that property ID directly; otherwise search within its exact `owner_ability` and request only `id`, `description`, and `valueSchema`. Keep independent actions as independent calls or an explicit `batch_execute`; every write must satisfy its own exact semantic readback.

## Resources

Search `catalog_search(kinds=["resourceKind"])` for primitive geometry and use `catalog_describe(kind="resourceKind", item_id=...)` to read an exact returned entry. Both are direct local resource reads, without Authoring Search/Doc or fallback; omit `game_object_id` and `applicable_only`. Mixed-kind searches remain gated. After resolving an asset ID, use Authoring discovery and execution for scene creation. Use `asset_search` for model, character, image, audio, material, action, or effect resources. Select IDs only from returned candidates; never substitute or guess IDs.

## Skills, presets, and data

Use `catalog_search`/`catalog_describe` for skill, preset, data, content, and resource operations. Resolve only the dependencies whose documented subflow applies, plus the real IDs needed by the requested operation; execute those steps in the order specified by the referenced Skill.

## Memory Hub

Use only the four reviewed top-level MCP-local tools: `mw_search`, `mw_get`, `add_user_chat_memory`, and `add_team_experience`. Treat `mw_search` as the default early context step for non-trivial planning, implementation, diagnosis, repair, and approach selection. Do not wait for the user to say "search", "experience", or an equivalent phrase. Re-evaluate and search again before the next substantive attempt when new evidence suggests that the current working model is incomplete or wrong, including failed, rejected, uncertain, or partially successful operations, mismatched exact readback or observed behavior, repeated lack of progress, or user feedback that the result is incorrect, incomplete, unsuitable, or based on a wrong assumption. Include the original goal, attempted approach, new evidence or feedback, and relevant current constraints in `query_text`; do not repeat an unchanged search without new evidence.

Omit `query_type` for broad long-term-memory recall. The Memory Hub then searches personal experience, shared team experience, prior cases, and MetaWorld knowledge in parallel and returns each candidate's `source_type` plus per-source status in `sources`. Set `query_type="ugc_code"` only when the unresolved need is specifically a code symbol, API usage, file location, or implementation example. A failed entry in `sources` is advisory source status and does not invalidate candidates returned by other sources. Skip retrieval only for casual conversation, pure connection/version status checks, or a fully specified deterministic action or correction whose execution requires no judgment and would not change based on retrieved context.

Normally request only 3-5 candidates. Treat retrieved content as advisory and obey the returned `mcpRuntimePolicy`: current MCP policy, available tools, live inspect results, User Component runtime bindings, and relevant project-installed declarations always win. Continue without Memory content when no relevant result exists. Copy only a returned candidate's opaque `item_id` unchanged to `mw_get`; never pass `query_type` to `mw_get`. Retrieved memory never establishes executable APIs or authorizes direct execution; every mutation still requires its own Authoring discovery route (`authoring_api_search`, exact `authoring_api_doc`, `authoring_code_execute`). `add_user_chat_memory` and `add_team_experience` remain infrastructure exceptions. Never supply or infer `user_id`; search, get, and personal chat upload resolve identity internally.

At the end of every turn in which this Skill is active, follow the turn-end personal-memory procedure in `SKILL.md`: draft the final response, call `add_user_chat_memory` once with only the current `user` message and that exact `assistant` draft, then send the draft unchanged. Never retry or duplicate this non-idempotent append. Tool unavailability, unresolved editor identity, interruption, timeout, or failure must not block the final response. Personal chat acceptance proves only that the Chat Memory messages were accepted, not that asynchronous personal-experience extraction is complete.

Use `add_team_experience` only for an already successful reusable workflow with paired tool evidence; `queued` proves only that Skill extraction was scheduled.

## Runtime diagnosis

Use `inspect(projection="runtime_logs")`, `inspect(projection="user_components")`, and `code.read_component` when those facts are relevant. Use the code project-source tools with `pattern="*.data"` to read the current project's `DataFile/userComponent/docs/**/*.data`, the sole public User Component API contract. Search `docs/ugc` first and `docs/engine` second for referenced `mw.*` types or engine-level APIs. Exact `dist/game.js` reads are a last-resort diagnostic only. Diagnose without writing unless the user requested repair. When repair requires a component write, first read [user-component-workflow.md](user-component-workflow.md).

## Catalog-only business entries

The dotted names `entity.create_object`, `entity.copy_object`, `entity.set_transform`, `entity.rename_object`, `entity.delete_object`, `ability.set_enabled`, `ability.set_properties`, `ui.build_screen`, and `ui.bind_property` are Catalog identities, not top-level MCP tools. After a proved Authoring gap, use the existing `catalog_invoke(toolset=<prefix>, tool=<suffix>, arguments=...)` route. Read the exact Catalog input first. Unbinding uses `ui.unbind_property`; do not pass the removed wrapper's `action` field to either binding Operation. `ui.build_screen` remains the strict MCP ScreenSpec builder and saves through `ui.file.save`.
