# Metaverse Antennae Editor

Operate the live editor through named semantic tools. Treat tool schemas, lookup results, and live inspect results as authoritative. Never invent object IDs, resource IDs, property paths, event APIs, or ability IDs.

When an approved fallback route uses `catalog_search`, pass `kinds` only as a non-empty native structured array such as `["operation"]`. Omit `kinds` to search all Catalog kinds. Never pass a scalar, comma-separated value, empty array, or JSON-encoded array string, and never repair validation failure by changing an array argument into a string.

## Core workflow

Choose the appropriate Authoring capability from the user's intended result:

- **Whole scene → Authoring ThreeScene first.** For a school, village, courtyard, street, campus, building complex or reference-image scene reconstruction, prefer `AuthoringThreeSceneService.run`, even without the words Three.js or code. Requests such as “帮我搭建一个学校”, “新建一个学校” and “复刻这张场景图” mean creating the spatial environment; do not reduce them to placing one school asset. Use intent-level `authoring_api_search`, exact `authoring_api_doc` for the returned `AuthoringThreeSceneService.run`, then `authoring_code_execute` with its documented runtimeAccess. The current binding is `globalThis.AuthoringSceneEditor.threeSceneService`; call `run(source, {sceneName, replacePrevious})`. Catalog `run_three_scene_script` and its description remain gated, with no ThreeScene bypass and no automatic execution of an intercepted call.
- **Isolated objects also use Authoring.** A simple square/cube, requested model, character or monster normally uses the appropriate asset-backed Authoring creation service. Suitable custom geometry, including a single tree or piece of furniture, may use the discovered ThreeScene service. Classify the complete request rather than the verb “新建/生成/create”; respect explicit asset-only, supplied-model or preset requirements.
- **Choose geometry and assets flexibly.** ThreeScene may generate buildings, trees, rocks, furniture, lamps and decorative forms. Choose per element by visual style, shape fidelity, materials, editability and cost; real assets are optional and may be interleaved with geometry. There is no fixed category split or mandatory structure-then-assets sequence. Functional water, lights, characters and gameplay use their actual Authoring capabilities. Preserve verified parts when an independent step fails.
- **Complete large scenes across Authoring executions.** The existing 499 non-root object limit is per `run`, not per scene. Count all Mesh/Group nodes and descendants; a Group does not combine its children into one counted object. Plan self-contained scripts by region or component within that capacity and the Authoring Execute outer-source/wait budgets. Use a shared coordinate plan, explicit `replacePrevious:false` when preserving previous work, and sequential bounded Execute calls until the requested scene is complete. Do not omit requested detail or stop at 499 cumulative objects; do not automatically split arbitrary source text, retry or substitute Catalog/Batch.
- **Verify the service result and retain IDs.** Check `run` summary `ok`, `exact` and `state`, not merely the outer `executed=true`. When identities or execution status are needed, discover/Doc `AuthoringThreeSceneService.readLastResult`, then use Authoring Execute to read snapshot pages by `offset/limit/nextOffset`, keeping the same `runId`. Retain needed IDs before the next run overwrites that snapshot. The outer Execute has a 64 KiB source limit and a maximum 30-second wait; timeout does not cancel generation. Reconcile `readLastResult` state before another run; never replay or fall back while execution is running or uncertain. Only intentional replacement of all generated batches registered by this VM uses `replacePrevious:true`.
- For a reference image, plan from its visible composition, proportions, colors and major forms. Exact project Authoring declarations are the first API reference; use domain Skill/Catalog references only when that discovery establishes a concrete missing reference fact. Do not make a ThreeScene Skill read or Catalog description a mandatory prerequisite to Search/Doc.

1. Treat `mw_search` as the default early context step for any non-trivial MetaWorld task involving planning, implementation, diagnosis, repair, or a choice between plausible approaches; do not wait for the user to request retrieval. Re-evaluate and call it again before the next substantive attempt whenever new evidence indicates that the current working model may be incomplete or wrong, including failed, rejected, uncertain, or partially successful operations, mismatched exact readback or observed behavior, repeated lack of progress, or user feedback that the result is incorrect, incomplete, unsuitable, or based on a wrong assumption. Include the original goal, attempted approach, observed evidence or feedback, and relevant current constraints in `query_text`; do not repeat an unchanged search without new evidence. Omit `query_type` for broad long-term-memory recall, and set `query_type="ugc_code"` only for a code symbol, API usage, file location, or implementation example. Skip retrieval only for casual conversation, pure connection/version status checks, or a fully specified deterministic action or correction whose execution requires no judgment and would not change based on retrieved context. Follow the Memory Hub routing in [tool-routing.md](references/tool-routing.md).
2. Use `system_status` only for explicit connection or version diagnostics.
3. Begin every Metaverse task with intent-level `authoring_api_search` and exact `authoring_api_doc`. Resource discovery is a direct business-data exception: use `asset_search` for external assets, `catalog_search(kinds=["resourceKind"])` without `game_object_id` or `applicable_only` for basic resources, and `catalog_describe(kind="resourceKind", item_id=...)` for an exact resource entry. These reads require neither Authoring discovery nor fallback. `capture` (viewport screenshots), `system_status`, and the Memory append tools are infrastructure exceptions, not alternate execution or discovery routes. `inspect` with exactly `projection="editor_mode"`, `"runtime_mode"`, or `"runtime_logs"` is a direct diagnostic exception. These diagnostics and `capture` require no Authoring discovery or fallback and preserve any pending route. Retrieved Memory Hub content is advisory context and never authorizes execution. Do not call Skill Resources, other Inspect projections, other core tools, non-resource Catalog Search/Describe, Catalog Invoke, or Batch before Authoring discovery proves a concrete capability gap.
4. Preserve the user's original intent before choosing an execution route. Treat one user-visible acceptance outcome as one root intent and begin with one precise end-to-end Search for that outcome. Lookup, creation, configuration, attachment, readback, and runtime wiring are dependency steps, not separate intents merely because they use different APIs or domains; search a dependency separately only when the root Search results prove that dependency unresolved. Every editor mutation—including create, modify, delete, batch, design, assemble, and other execution work—must be covered by the root intent's `authoring_api_search`, exact `authoring_api_doc`, and `authoring_code_execute`, followed by bounded exact semantic readback. Do not repeat synonymous Search queries after an exact callable symbol is found. Doc each final callable symbol once. Treat compact Doc `pendingTypes` as informational, not a to-do list: expand only a type whose missing fields, signature, runtime access, constraint, or readback semantics actually block safe code generation. Never recursively Doc the complete type graph, basic engine types, display-only DTOs, or types unused by the planned body. Within the same current user task, reuse exact Search/Doc results already returned only when the editor session, active project and level are unchanged, the requested semantics use the same documented symbols, no declaration-changing operation occurred, and no execution or transport uncertainty exists. Keep a small current-task evidence set keyed by exact symbol so the same symbol is not documented twice. Never reuse discovery across tasks, turns, restarts, `EDITOR_LEVEL_CHANGED`, active-project changes, new symbols or semantics, or as evidence for an unrelated captured fallback route; only the exact Catalog continuation in item 5 may retain discovery evidence. Stage execution at real write boundaries and give every mutation its own bounded Exec and exact semantic readback without splitting the root intent.
5. Skill Resources, Inspect, and Catalog are fallback reference/read paths, except for the direct resource discovery and diagnostic reads above. Enter them through captured `authoring_route_fallback` after Search/Doc proves the exact missing operation, identity, schema, terminology, or readback semantic. A successful Catalog lookup may continue directly to Describe of its exact returned kind/id; the immediately following Invoke of the described invoke target is still captured once, but retains this chain's Search/Doc evidence. Follow the bounded Catalog continuation in [tool-routing.md](references/tool-routing.md); unrelated calls never inherit that evidence. Prefer the narrowest complete fallback lookup. After a successful read-only fallback supplies missing reference facts, continue the original task: reuse Search/Doc still in context under item 4's validity conditions; discover only newly needed symbols or missing constraints. Each mutation still requires bounded authoring_code_execute and exact semantic readback. Fallback facts alone never establish callable APIs or authorize another fallback. Memory Hub retrieval (`mw_search`/`mw_get`) is the proactive context exception: it may run early as item 1 describes, but its content remains advisory and never establishes executable APIs.
6. Except for the resource discovery and infrastructure/diagnostic exceptions above, a named semantic tool or Catalog handler may run only through `authoring_route_fallback` after the current captured route's own searched and documented public Authoring declarations prove a concrete capability gap. ThreeScene follows this same workflow: `run_three_scene_script`, its Catalog description and Batch are intercepted; discover and execute `AuthoringThreeSceneService.run` when it covers the scene request. Search/Doc reuse may guide public Authoring execution, but never authorizes a fallback. If the route gate returns `AUTHORING_ROUTE_REQUIRED`, treat `routing.queries` only as optional, non-exhaustive starting hints rather than a required search set, whitelist, or capability boundary; the list may be empty. Search from the original intent, inspect exact hits, and follow relevant declarations, parameter types, and dependencies freely. Never fall back after `executed=true` or execution uncertainty.
7. For gameplay or multi-step work, preserve the root intent across domains and compose the discovered public APIs into that complete workflow. Split discovery only at a genuinely independent authorization, destructive-write, editor-mode, external-wait, or user-visible acceptance boundary; never split merely because implementation steps use different tools, resources, components, or APIs. When optional reference material is required, identify the responsible domains, read only their needed `antennae://skills/{skill}/index` and `/body` sections, and load a dependency body only when its conditional subflow is part of the user's request and the final implementation will actually consume that domain resource. Treat each write Operation's own semantic readback as its completion boundary.
8. Execute the smallest valid write. A write is complete only when its own response is `succeeded_verified`; do not add a blanket scene-overview read.

### Authoring context discipline

- For player initial weapons, health, or other inheritable abilities, first locate and verify the existing scene object with `playerStart` through Authoring. Mount and configure the corresponding abilities (for example, `WeaponSlotAbility` and `health`) on that player-start object so the runtime player inherits them. Do not identify it by name alone or substitute a global script for player-start ability configuration. Changes to an individual player's state during play must target that actual runtime player entity.
- Keep `authoring_api_search` results bounded with `limit <= 8`.
- Search may return `abilityNames` from the component's generated Ability assembly constraints. Use these names instead of guessing from component names; multiple names are ownership candidates. An omitted field means no proven mapping in the declaration. Ownership alone does not establish property binding support, supported target roles, or whether an Ability can be added; read exact constraints when those facts are needed.
- Use compact Authoring Doc by default. Do not request `detail="full"` for an entire class; expand only an exact blocking symbol or referenced type when compact detail is insufficient for safe execution.
- When several exact symbols are already known, pass 1-8 strings together in `authoring_api_doc.symbol` to share one declaration snapshot. Batch results share the declaration revision in `context`; inspect `allSucceeded` and each result's `ok`, retaining successful documents when another item fails. Duplicate symbols are returned once in input order. A response-budget error requires a separate Doc for that symbol. Do not fill batches with unused types or repeat successful reads. Search remains compact.
- When exact target IDs are already known and still valid in the current task context, do not call `getAllEntities()`.
- In the outer JavaScript body passed to `authoring_code_execute`, use the directly injected `IScene` and `mw` root bindings. Use `IScene.getCurrentScene()`, never `api.IScene`, and access editor services through `globalThis.AuthoringSceneEditor`. This restriction does not apply to `api.*` text inside a User Component source string; persisted User Component code must continue to follow its current `.data` declarations and generated template. No `api` namespace is injected into the Authoring execution body or its helper functions/callbacks: do not use `api.*` there (including `api.IScene`, `api.mw`, or `api.AuthoringSceneEditor`). For other symbols and services, follow the exact Doc `runtimeAccess`; a declaration name alone does not establish an executable global binding. Do not construct an `api` alias to bypass this rule or globally strip `api.` from source: User Component source strings have their own declared runtime context.
- When one `authoring_code_execute` body intentionally combines creation and configuration, preflight every required outer binding, service, method, editor state, and known input before the first mutation. Keep the created object reference and ID in scope, and perform bounded cleanup in the same body if later configuration fails. This reduces partial writes but is not transactional protection against timeout, transport loss, or editor interruption; uncertainty still requires exact reconciliation and forbids blind retry.
- Keep `authoring_code_execute` results surgical: return only changed fields, aggregate counts, and mismatches needed for exact semantic readback. Do not return complete entities, component graphs, transforms, bounds, or material arrays unless the requested verification requires them.
- For ordinary asset-backed edit-mode object creation, discover and use the verified `AuthoringSceneCreationService.create` entry at `globalThis.AuthoringSceneEditor.creationService`. Supply a real assetId, name and transform; never turn asset-search `kind` into a tag or supply guessed `abilityTag`/`ObjTag`. The entry resolves resource metadata, uses the standard editor creation command and verifies registration. If this public entry is unavailable, report the capability gap rather than substitute `sceneModule.createObj`, raw command parameters, `IScene.createEntity` or engine spawning. Runtime User Component entity creation still follows its own declarations.
- Creation and configuration may share one Execute, but check the creation result before continuing. On `ok=false`, return its stage, gameObjectId, mismatches and cleanup status and stop attaching components, moving or saving. Keep successful creation IDs in any subsequent failure result. Cleanup uses standard editor deletion and exact absence readback; uncertain cleanup forbids automatic recreation. Report visibility, semantic registration, programmatic selection, actual viewport clicking, save/reopen and PlayMode as distinct evidence; never infer the latter from `ok=true`.
- After successful exact readback, do not add a broad scene overview or full-scene Inspect. If readback reports a mismatch, narrow-read only the affected target and fields before deciding whether another mutation is safe.
- Reuse completed Search/Doc evidence within the same current user task only under the unchanged-context conditions above.
- Stop when the requested stage and its required readback are complete; do not broaden the verification scope without a concrete failure or an explicit user request.

`capture` remains available for visual acceptance when useful. Its use does not replace semantic readback, and this context discipline does not require or forbid it.

For Memory Hub search, readback, or explicit memory upload, use only the four top-level Memory tools documented in [tool-routing.md](references/tool-routing.md). They are MCP-local HTTP capabilities, not editor Operations, and never accept caller-supplied `user_id`.

## Turn-end personal memory

For every turn in which this Skill is active, make exactly one best-effort call to `add_user_chat_memory` immediately before the final response. First draft the complete final response, then append only the current turn's user message and that draft as ordered `user` and `assistant` messages. Do not include system prompts, commentary, tool calls, tool results, prior turns, or inferred facts. After the call, send the same drafted response unchanged.

This append is non-idempotent. Never retry it, including after a timeout or uncertain result, and never make a second call for the same turn. Omit `username` unless an authoritative display name is already available and first-time provisioning requires it. If the tool is unavailable, the editor user cannot be resolved, the turn is interrupted before a final response, or the call fails, continue with the final response without claiming that memory was saved. This Skill instruction is a best-effort pre-final hook, not a guaranteed host-level after-turn event.

Read the Memory Hub section of [tool-routing.md](references/tool-routing.md) whenever retrieval may help, and use the rest of that reference when selecting tools for a multi-domain task. Read [verification.md](references/verification.md) before any write or repair.

For `ui.bind_property`, when the source kind is known, read only its branch with `catalog_describe(kind="operation", item_id="ui.property.bind", projection="input_only", selectors=[{"field":"kind","value":<source kind>}])`. For `ui.build_screen`, call `catalog_describe(kind="tool", item_id="build_screen", projection="input_only")` first; read `antennae://ui/schema` only when constructing a custom tree that genuinely uses definitions or multiple node branches not retained by the exact input description. The full Resource remains authoritative for those requested branches, but it is not the default routing read.

## Custom runtime logic

Prefer existing official components and systems. Only after deciding that the requested behavior requires creating or modifying a User Component, read [user-component-workflow.md](references/user-component-workflow.md) before the first component write. Do not load that workflow for ordinary scene, UI, resource, property configuration, or read-only inspection tasks.

## Safety boundary

- If an editor-backed tool returns `EDITOR_LEVEL_CHANGED`, the editor reports the user-facing change from `details.previousLevelDisplayName` to `details.currentLevelDisplayName`, plus stable level IDs and file names, and the attempted operation was not sent. Tell the user which display-named level changed, discard prior scene assumptions, call `inspect` to re-scan the current project and resolve fresh target IDs before continuing; non-inspect editor operations remain blocked until that read succeeds.
- Do not use private or removed execution paths when a named semantic tool or Catalog operation exists.
- Do not use a successful transport response as proof of editor state; require semantic readback.
- Do not delete, overwrite, or broadly rewrite editor content unless the user requested that exact scope.
- Do not claim completion when the contract does not match, the bridge is not ready, or required readback is incomplete.
- Any `uncertain` result must be reconciled with an explicit narrow read before deciding whether another write is safe.
